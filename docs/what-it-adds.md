# What the kit adds to an app

What `npx agentic-mobile-kit init` puts into a React Native app, bare or Expo. CI files come only with `--ci github`, `--ci codemagic` or, for Expo apps, `--ci eas`.

| Area | What you get |
|---|---|
| Project knowledge | `AGENTS.md` (with a one-line `CLAUDE.md`): commands, the definition of done and the rules. `docs/amk/`: product, tech stack, structure, conventions, the app's own words (glossary), how it looks (design system), decisions, known issues, React Native rules and team process. The `m-onboard` skill drafts the first six from the code. Callstack's React Native skills. Agents ask their questions as options to pick from where the tool has a question tool. Expo apps get Expo rules (`docs/amk/expo.md`) and Expo's own skills for routing, SDK upgrades and native modules instead of the bare-only parts. |
| Specs | `specs/<id>/` for each feature: user stories, use cases and requirements, design with its test plan, tasks, a Maestro flow and a handoff file. Approved requirements are committed as such, and later changes are logged with their reason and impact. Before a feature's screens are designed, the user picks their UI/UX level: Simple (the default), Mixed or Premium. A living spec of what the app does now, in `specs/current/`. `specs.js`: `check`, `merge`, `status`, `tests` (what tests the areas a change touches) and `flow` (a flow with a block per scenario). To plan all, then build: `specs/plan.md` on a `plan` branch (the feature map, the shared design, what's approved up front), `m-feature plan` and `build`, the `m-spec-writer` subagent that drafts each planned feature in a fresh context, `specs.js check --plan` (the specs against each other) `specs.js start` (the next ready feature, branched with its spec as approved) and `specs.js import` (a CSV or Trello export to plan from, as data). `scripts/amk/autopilot.js` builds the approved features unattended: a fresh session per feature under the build's permission profile, with stop reasons, a stall watchdog, notes and a stop file, notifications, and blocked questions as issues when turned on; the stop hook keeps an unattended feature going, and a hook brings the handoff back after a compaction. `pr.js` follows each pull request: its checks (a failure's log, for the fix), its review comments, auto-merge for a team, and `main` merged into the stacked branches whose parent merged. Before the features, `autopilot.js` answers its pull requests' unanswered review comments and works through the bug queue (issues labelled `amk-fix`, read by `issue.js` as data), each to a pull request. A design records the API contract of calls the backend doesn't have yet, and `verify.sh --mock` checks the feature against the app's mock mode (`.amk-mock`). |
| Tests | `m-test` runs the checks and the device flows of a change and the areas it touches; the read-only `m-tester` gives each scenario a status and the report (`specs/<id>/test-report.md`) says Ready or Not ready. `coverage.js` keeps coverage floors, so deleted or weakened tests fail `m-test` and CI. Releases test before their PR. A pass against the mock API is "passed (mock API)", and a release lists the scenarios that never ran against the real backend. |
| Device checks | `verify.sh`: lint and tests, release builds on an iPhone simulator and an Android emulator (any product flavor or iOS scheme; in Expo apps, after generating the native projects), the feature's Maestro flow on each screen the app supports (phone and tablet, upright and turned), and screenshots in `.amk/evidence/<id>/`. As many devices at the same time as the machine's memory fits (2 from 16 GB), in rounds, each checked by its own `m-device-checker` subagent; with room to spare, a device's flows split into parts, each on a device of its own. A real iPhone or iPad when named, with a build Xcode signs for it, its flows run through maestro-runner, and the app's crash reports from the device. A failed flow shows the step and what Maestro said, and the screen then; each run writes `report.md` (each flow's result and screenshots) and `junit.xml`, and CI shows a summary. `--tags smoke` checks only the flows tagged so, and `--spec a,b` several specs' flows at once. A flow that passes only when run again is reported as flaky. A build stops first when the disk is nearly full. `quick --related` runs only the tests of the changed files. Each check lists the screenshots that differ from the approved ones (`verify.sh approve`). On Android screens, the view tree after each screenshot shows controls without a label and tap areas under 48 dp, as warnings |
| React Native checks | `rn-check.js`, in `verify.sh quick`: the lines a branch changes, in code and in Maestro flows (Maestro's own syntax check, subflows that aren't there, taps by text, and every scenario of a touched spec with its steps, an assertion and a screenshot), for removed or private React Native APIs, tokens in plain storage, secrets and base64 images in code (these fail), and labels, index keys, empty `catch`, timers and `any`, plus Apple's and Android's guidelines (text under 11 points or capped scaling, small tap areas, back gestures turned off, modals that back can't close, controls without their state, permissions asked on screen open, looping animations that ignore Reduce Motion) as warnings. A line the user keeps carries `// amk-ok <date>: <reason>`, asked about again after two weeks. Warnings too for a source file over 400 lines that's new or grows, and a function more complex than 20 that's new or got more complex, with the files already over in `.amk-size-caps` |
| Releases | `release-check.js` catches what store review would reject (permission texts, the privacy manifest, account deletion, Sign in with Apple next to a social login, tracking without the ATT prompt, Google Play's restricted permissions, including ones libraries add, foreground service types, 16 KB pages), and signing keys left in git. Changelog and store notes come from commits (git-cliff). `set-version.sh` sets versions. Signed builds come from `release-build.sh` or Codemagic (`--ci codemagic`). Test builds for testers: Codemagic's, to Firebase App Distribution and TestFlight's internal testing, each merge to `main` once turned on; for Expo apps, an EAS preview of each pull request with a comment to open it (`--ci eas`). |
| Guardrails in AI tools | Hooks that block destructive commands and secret files and remind the agent about the handoff, permission rules, and read-only reviewers of the code and of how screens look, generated with rulesync. In Expo apps, edits to the generated `ios/` and `android/` are blocked and EAS commands need a person's OK. |
| Git hooks | Before a commit: secrets, signing files, Xcode project files, files renamed only in letter case, ESLint, spec format. Before a push: typecheck and tests. With husky, lefthook or simple-git-hooks, they run from those. |
| Upkeep | `metrics.js` for the monthly review (PR size, review wait, CI failures, reopened issues, approval to PR, the agents' PRs merged and reworked), `m-learn review` (what reviews keep finding, as checks), `m-onboard check` (docs that are no longer true), `m-report` (a status report for the client, which a person sends), and a weekly pull request with the kit's next version (`--ci github`). In apps with language files, `rn-check` warns about a key one language lacks. |
| CI (`--ci github`) | Lint, typecheck, tests, a secret scan, a tool-config check, a 600-line PR limit (`large-pr` label; the kit's own update PRs are left out), Android and iOS builds, each only when the change calls for it, summed up by one `checks` job for branch protection; nightly end-to-end tests (`e2e` label), with an issue when they fail; the `amk-ready` label for auto-merge after a solo developer's review; and a PR template |
| AI jobs in CI (`--ci github,ai`, optional) | An AI review that comments on each ready pull request, and an AI fix for a dependency update whose CI fails (no version changes). They never approve, and pause themselves after three failures in a row |
| Everyday scripts | `install-deps.sh`, `pm-run.sh`, `ios-build.sh`, `pod-install.sh`, `prebuild.sh` (Expo), `redact.js` (secrets out of text that leaves the machine, and outside text marked as data for agents), `tool-configs.js` (finishes the tool configs rulesync generates) |

All scripts are in `scripts/amk/`. The [team guide](team-guide.md) has the details.
