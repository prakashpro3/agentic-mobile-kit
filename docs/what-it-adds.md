# What the kit adds to an app

What `npx agentic-mobile-kit init` puts into a React Native app, bare or Expo. CI files come only with `--ci github` or `--ci codemagic`.

| Area | What you get |
|---|---|
| Project knowledge | `AGENTS.md` (with a one-line `CLAUDE.md`): commands, the definition of done and the rules. `docs/amk/`: product, tech stack, structure, conventions, the app's own words (glossary), decisions, known issues, React Native rules and team process. The `m-onboard` skill drafts the first five from the code. Callstack's React Native skills. Expo apps get Expo rules (`docs/amk/expo.md`) and Expo's own skills for routing, SDK upgrades and native modules instead of the bare-only parts. |
| Specs | `specs/<id>/` for each feature: requirements, design, tasks, a Maestro flow and a handoff file. Before a feature's screens are designed, the user picks their UI/UX level: Simple (the default), Mixed or Premium. A living spec of what the app does now, in `specs/current/`. `specs.js`: `check`, `merge`, `status`. |
| Device checks | `verify.sh`: lint and tests, release builds on an iPhone simulator and an Android emulator (any product flavor or iOS scheme; in Expo apps, after generating the native projects), the feature's Maestro flow on each screen the app supports (phone and tablet, upright and turned), and screenshots in `.amk/evidence/<id>/`. As many devices at the same time as the machine's memory fits (2 from 16 GB), in rounds, each checked by its own `m-device-checker` subagent; with room to spare, a device's flows split into parts, each on a device of its own. A real iPhone or iPad when named, with a build Xcode signs for it, its flows run through maestro-runner, and the app's crash reports from the device. A failed flow shows the step and what Maestro said, and the screen then; each run writes `report.md` (each flow's result and screenshots) and `junit.xml`, and CI shows a summary. `--tags smoke` checks only the flows tagged so. On Android screens, the view tree after each screenshot shows controls without a label and tap areas under 48 dp, as warnings |
| React Native checks | `rn-check.js`, in `verify.sh quick`: the lines a branch changes, in code and in Maestro flows (Maestro's own syntax check, subflows that aren't there, taps by text, and every scenario of a touched spec with its steps, an assertion and a screenshot), for removed or private React Native APIs, tokens in plain storage, secrets and base64 images in code (these fail), and labels, index keys, empty `catch`, timers and `any`, plus Apple's and Android's guidelines (text under 11 points or capped scaling, small tap areas, back gestures turned off, modals that back can't close, controls without their state, permissions asked on screen open, looping animations that ignore Reduce Motion) as warnings. A line the user keeps carries `// amk-ok <date>: <reason>`, asked about again after two weeks |
| Releases | `release-check.js` catches what store review would reject (permission texts, the privacy manifest, account deletion, Sign in with Apple next to a social login, tracking without the ATT prompt, Google Play's restricted permissions, including ones libraries add, foreground service types, 16 KB pages), and signing keys left in git. Changelog and store notes come from commits (git-cliff). `set-version.sh` sets versions. Signed builds come from `release-build.sh` or Codemagic (`--ci codemagic`). |
| Guardrails in AI tools | Hooks that block destructive commands and secret files and remind the agent about the handoff, permission rules, and a read-only reviewer, generated with rulesync. In Expo apps, edits to the generated `ios/` and `android/` are blocked and EAS commands need a person's OK. |
| Git hooks | Before a commit: secrets, signing files, Xcode project files, files renamed only in letter case, ESLint, spec format. Before a push: typecheck and tests. With husky, lefthook or simple-git-hooks, they run from those. |
| CI (`--ci github`) | Lint, typecheck, tests, a secret scan, a tool-config check, a 600-line PR limit (`large-pr` label), Android and iOS builds, nightly end-to-end tests (`e2e` label), and a PR template |
| Everyday scripts | `install-deps.sh`, `pm-run.sh`, `ios-build.sh`, `pod-install.sh`, `prebuild.sh` (Expo) |

All scripts are in `scripts/amk/`. The [team guide](team-guide.md) has the details.
